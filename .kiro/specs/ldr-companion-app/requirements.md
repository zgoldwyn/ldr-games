# Requirements Document

## Introduction

The LDR Companion App is a cross-platform application (mobile and desktop) designed for people in long-distance relationships. Two people link their accounts into an exclusive one-to-one pairing and gain access to shared features: real-time two-player games, asynchronous turn-based two-player games, themed scored quizzes, and a shared calendar of important relationship dates with reminders. A user can be paired with exactly one partner at any given time. All games and quizzes are played online between the two paired partners.

A User may use the app on both mobile and desktop, and Account data remains consistent across platforms; however, only one authenticated session per Account may be active at a time, so establishing a new session ends any previous session. Real-time games require both Partners to be present in the same active session, whereas asynchronous turn-based games progress over time and may advance while only one Partner has an active session.

This document defines the functional and quality requirements for the feature set. Implementation details (frameworks, protocols, data stores) are deliberately excluded and will be addressed in the design phase.

## Glossary

- **System**: The LDR Companion App as a whole, including mobile and desktop clients and supporting backend services.
- **Account**: A registered user identity with unique credentials.
- **User**: A person who owns an Account and interacts with the System through a client.
- **Client**: A mobile or desktop instance of the System used by a User.
- **Authenticated_Session**: An active login state that grants a single Client access to an Account's shared features. At most one Authenticated_Session may exist per Account at any time.
- **Pairing**: An exclusive one-to-one link between two Accounts that grants access to shared features.
- **Partner**: The other User in a Pairing relative to a given User.
- **Pairing_Invitation**: A time-limited request generated by one Account to establish a Pairing with another Account.
- **Game**: A two-player interactive activity played between the two Users in a Pairing. A Game is either a Real_Time_Game or an Asynchronous_Game.
- **Real_Time_Game**: A Game in which both Partners participate simultaneously within the same active Session.
- **Asynchronous_Game**: A Game in which Partners take Turns separately over time, where each Turn depends on the other Partner having completed the preceding Turn (for example Battleship or a drawing game).
- **Game_Session**: A single instance of a Game being played by both Partners. A Game_Session is either a Real_Time_Game_Session or an Asynchronous_Game_Session.
- **Real_Time_Game_Session**: A single instance of a Real_Time_Game being played by both Partners.
- **Asynchronous_Game_Session**: A single instance of an Asynchronous_Game being played by both Partners over time.
- **Turn**: A single move or set of permitted actions taken by one Partner during an Asynchronous_Game_Session.
- **Active_Turn_Holder**: The Partner whose Turn it currently is in an Asynchronous_Game_Session, and who is the only Partner permitted to take the next Turn.
- **Quiz**: A themed, scored set of Quiz_Questions that both Partners complete in two phases: a self-answer phase and a guessing phase.
- **Quiz_Question**: A single multiple-choice or very short answer question belonging to exactly one Quiz.
- **Quiz_Session**: A single instance of a Quiz being taken within a Pairing.
- **Self_Answer**: The answer a Partner records for a Quiz_Question about themselves during the self-answer phase.
- **Guess**: A Partner's prediction, recorded during the guessing phase, of the other Partner's Self_Answer for a Quiz_Question.
- **Score**: The number of points a Partner has accumulated in a Quiz_Session, where one point is awarded for each Guess that matches the other Partner's Self_Answer.
- **Relationship_Date**: A calendar entry, owned by a Pairing, marking a date of significance (for example an anniversary or birthday).
- **Reminder**: A scheduled notification associated with a Relationship_Date.
- **Notification**: A message delivered to a User's Client to inform the User of an event.
- **Account_Deletion**: The permanent removal of an Account and its data at the request of the Account's own User. Distinct from dissolving a Pairing, which ends the link between two Accounts but retains both Accounts and their individual data.
- **Authentication_Service**: The System component responsible for verifying Account credentials.
- **Pairing_Service**: The System component responsible for creating, enforcing, and dissolving Pairings.
- **Sync_Service**: The System component responsible for keeping shared data consistent across a User's Clients and between Partners.

## Requirements

### Requirement 1: Account Registration

**User Story:** As a new user, I want to create an account, so that I can access the app and link with my partner.

#### Acceptance Criteria

1. WHEN a User submits registration details with a syntactically valid email address not associated with any existing Account and a password that is 12 to 128 characters long and contains at least one uppercase letter, at least one lowercase letter, at least one digit, and at least one non-alphanumeric character, THE Authentication_Service SHALL create a new Account, return a success confirmation within 5 seconds, and place the Account in an unpaired state.
2. IF a User submits registration details with an email address already associated with an existing Account, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error identifying the email as already registered.
3. IF a User submits a password shorter than 12 characters, longer than 128 characters, or missing at least one uppercase letter, one lowercase letter, one digit, or one non-alphanumeric character, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error describing each unmet password criterion.
4. IF a User submits registration details with an email address that is not in a valid email format, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error indicating that the email address format is invalid.
5. IF a User submits registration details in which the email address or the password is empty or absent, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error identifying each missing required field.
6. THE Authentication_Service SHALL store passwords using a one-way cryptographic hash and SHALL never store or return the plaintext password.

### Requirement 2: Account Authentication

**User Story:** As a registered user, I want to sign in securely, so that only I can access my account.

#### Acceptance Criteria

1. WHEN a User submits credentials consisting of an email address and a password that match an existing Account, THE Authentication_Service SHALL grant access, establish an Authenticated_Session for that Client, and complete authentication within 3 seconds under normal network conditions.
2. IF a User submits credentials that do not match any existing Account, THEN THE Authentication_Service SHALL deny access and return an authentication-failed error that does not indicate whether the email address or the password was incorrect.
3. IF a User submits non-matching credentials for the same Account on 5 consecutive attempts within a 15-minute window, THEN THE Authentication_Service SHALL temporarily lock authentication for that Account for 15 minutes and return an error indicating that the Account is temporarily locked.
4. WHEN a User signs out, THE Authentication_Service SHALL terminate the Authenticated_Session for that Client within 3 seconds.
5. WHILE a User has no valid Authenticated_Session, THE System SHALL deny access to shared features and direct the User to the sign-in interface.
6. WHILE an Authenticated_Session has had no User activity for 30 consecutive days, THE Authentication_Service SHALL invalidate the Authenticated_Session and require the User to sign in again before granting further access.
7. THE Authentication_Service SHALL maintain at most one active Authenticated_Session per Account at any time.
8. WHEN a User successfully authenticates on a Client for an Account that already has an active Authenticated_Session on another Client, THE Authentication_Service SHALL terminate the existing Authenticated_Session before establishing the new Authenticated_Session, so that only the newly authenticated Client retains access.
9. WHEN the Authentication_Service terminates an Authenticated_Session because a new Authenticated_Session was established for the same Account, THE System SHALL deny further access to shared features on the terminated Client and direct that Client to the sign-in interface within 5 seconds while that Client has network connectivity.

### Requirement 3: Partner Pairing

**User Story:** As a user, I want to link my account with my partner, so that we can share games, quizzes, and dates.

#### Acceptance Criteria

1. WHEN an authenticated User who is not currently in a Pairing requests to invite a Partner, THE Pairing_Service SHALL generate a unique Pairing_Invitation that is valid for 72 hours from its creation.
2. WHEN a User accepts a Pairing_Invitation within 72 hours of its creation and neither Account is currently in a Pairing, THE Pairing_Service SHALL create a Pairing linking the two Accounts.
3. IF a User attempts to accept a Pairing_Invitation while already in a Pairing, THEN THE Pairing_Service SHALL reject the request, leave the pairing state of both Accounts unchanged, and return an error stating that the Account is already paired.
4. IF a User attempts to create or accept a Pairing_Invitation for an Account that is already in a Pairing, THEN THE Pairing_Service SHALL reject the request, leave the pairing state unchanged, and return an error stating that the target Account is already paired.
5. IF a User accepts a Pairing_Invitation more than 72 hours after its creation, THEN THE Pairing_Service SHALL reject the request, leave the pairing state unchanged, and return an expiration error.
6. THE Pairing_Service SHALL ensure that each Account is a member of at most one active Pairing at any time.
7. IF an authenticated User who is already in a Pairing requests to invite a Partner, THEN THE Pairing_Service SHALL reject the request and return an error stating that the Account is already paired.
8. WHEN a Pairing is created from a Pairing_Invitation, THE Pairing_Service SHALL invalidate that Pairing_Invitation so that it cannot be used to create another Pairing.

### Requirement 4: Partner Unlinking

**User Story:** As a user, I want to unlink from my partner, so that I can end the pairing or link with someone else.

#### Acceptance Criteria

1. WHEN an authenticated User in a Pairing confirms a request to unlink, THE Pairing_Service SHALL dissolve the Pairing and revoke shared-feature access for both Accounts within 5 seconds.
2. WHEN a Pairing is dissolved, THE Pairing_Service SHALL deliver a Notification to each former Partner's Authenticated_Session indicating that the Pairing has ended.
3. WHEN a Pairing is dissolved, THE Pairing_Service SHALL set both former Partner Accounts to an unpaired state such that each Account may create or accept a new Pairing_Invitation.
4. WHEN a Pairing is dissolved, THE System SHALL retain each former Partner Account's individual data and revoke both former Partners' access to all data owned by the former Pairing.
5. IF a former Partner has no Authenticated_Session at the time a Pairing is dissolved, THEN THE Pairing_Service SHALL deliver the Pairing-ended Notification when that Partner next establishes an Authenticated_Session.
6. IF a Game_Session or Quiz_Session is active for a Pairing when that Pairing is dissolved, THEN THE System SHALL terminate the active Session and notify both former Partners that the Session has ended.

### Requirement 5: Cross-Platform Access and Synchronization

**User Story:** As a user, I want to use the app on both mobile and desktop, so that my data stays consistent everywhere even though only one session is active at a time.

#### Acceptance Criteria

1. WHEN a User establishes an Authenticated_Session on a mobile Client or on a desktop Client, THE System SHALL present the same Account data and shared data to that Authenticated_Session regardless of platform.
2. WHEN shared data is changed during an Authenticated_Session, THE Sync_Service SHALL persist the change so that it is present when the User next establishes an Authenticated_Session on any Client.
3. WHEN shared data is changed by one Partner, THE Sync_Service SHALL propagate the change to the other Partner's Authenticated_Session within 5 seconds while both Partners' Clients have network connectivity.
4. IF a Client loses network connectivity, THEN THE System SHALL display a connectivity-lost indicator and retain all local changes in a synchronization queue until network connectivity is restored.
5. WHEN a Client regains network connectivity, THE Sync_Service SHALL synchronize all queued changes within 10 seconds of connectivity restoration and resolve conflicting changes to the same shared data item using a last-write-wins policy based on change timestamps.
6. IF two conflicting changes to the same shared data item have identical change timestamps, THEN THE Sync_Service SHALL apply a deterministic resolution so that both Partners' Authenticated_Sessions converge to the same value.

### Requirement 6: Real-Time Two-Player Game Sessions

**User Story:** As a paired user, I want to play games with my partner in real time, so that we can have fun together across the distance.

#### Acceptance Criteria

1. WHILE a User is in a Pairing, THE System SHALL present the list of available Real_Time_Games to both Partners.
2. WHEN a User in a Pairing selects a Real_Time_Game and invites the Partner, THE System SHALL create a Real_Time_Game_Session in a pending state and deliver an invitation Notification to the Partner within 5 seconds while both Clients have network connectivity.
3. WHEN both Partners have joined a pending Real_Time_Game_Session within 60 seconds of the invitation, THE System SHALL transition the Real_Time_Game_Session to an active state, start the Real_Time_Game, and present identical game state to both Partners.
4. WHEN one Partner performs a valid move in an active Real_Time_Game_Session, THE System SHALL update the game state and reflect the move on both Partners' Clients within 2 seconds while both Clients have network connectivity.
5. IF a User attempts to start a Real_Time_Game_Session while not in a Pairing, THEN THE System SHALL reject the request and return an error stating that a Partner is required.
6. IF a Partner's Client has no network connectivity with the System for 30 continuous seconds during an active Real_Time_Game_Session, THEN THE System SHALL pause the Real_Time_Game_Session, deliver a Notification to the remaining Partner, and preserve the current game state.
7. WHEN a disconnected Partner rejoins a paused Real_Time_Game_Session within 5 minutes of the pause, THE System SHALL resume the Real_Time_Game_Session from the preserved game state and present identical game state to both Partners.
8. WHEN a Real_Time_Game_Session reaches a terminal state, THE System SHALL record the outcome and present the result to both Partners.
9. IF the invited Partner does not join a pending Real_Time_Game_Session within 60 seconds of the invitation, THEN THE System SHALL cancel the Real_Time_Game_Session and deliver a Notification to the inviting Partner indicating that the invitation expired.
10. IF a disconnected Partner does not rejoin a paused Real_Time_Game_Session within 5 minutes of the pause, THEN THE System SHALL terminate the Real_Time_Game_Session, record it as ended without a completed outcome, and deliver a Notification to both Partners.
11. IF a Partner attempts an invalid move in an active Real_Time_Game_Session, THEN THE System SHALL reject the move, retain the current game state unchanged, and return an error indicating that the move is invalid.

### Requirement 7: Asynchronous Turn-Based Game Sessions

**User Story:** As a paired user, I want to play turn-based games with my partner asynchronously, so that we can play together even when we are online at different times.

#### Acceptance Criteria

1. WHILE a User is in a Pairing, THE System SHALL present the list of available Asynchronous_Games to both Partners.
2. WHEN a User in a Pairing selects an Asynchronous_Game and invites the Partner, THE System SHALL create an Asynchronous_Game_Session, designate one Partner as the Active_Turn_Holder according to the Asynchronous_Game's rules, and deliver an invitation Notification to the Partner.
3. WHILE an Asynchronous_Game_Session is active, THE System SHALL allow an Asynchronous_Game_Session to progress whether both Partners have an Authenticated_Session or only one Partner has an Authenticated_Session.
4. WHILE a Partner is the Active_Turn_Holder in an active Asynchronous_Game_Session, THE System SHALL permit that Partner to take exactly one Turn.
5. WHEN the Active_Turn_Holder completes a valid Turn in an active Asynchronous_Game_Session, THE System SHALL record the Turn, update the game state, and transfer the Active_Turn_Holder designation to the other Partner.
6. WHEN the Active_Turn_Holder completes a valid Turn in an active Asynchronous_Game_Session, THE System SHALL deliver a Notification to the other Partner indicating that it is now that Partner's Turn, within 5 seconds while that Partner's Client has network connectivity, and otherwise deliver the Notification when that Partner next establishes an Authenticated_Session.
7. IF a Partner who is not the Active_Turn_Holder attempts to take a Turn in an active Asynchronous_Game_Session, THEN THE System SHALL reject the Turn, retain the current game state unchanged, and return an error stating that it is not that Partner's Turn.
8. IF the Active_Turn_Holder attempts an invalid Turn in an active Asynchronous_Game_Session, THEN THE System SHALL reject the Turn, retain the current game state unchanged, and return an error indicating that the Turn is invalid.
9. IF a User attempts to start an Asynchronous_Game_Session while not in a Pairing, THEN THE System SHALL reject the request and return an error stating that a Partner is required.
10. WHEN an Asynchronous_Game_Session reaches a terminal state, THE System SHALL record the outcome and present the result to each Partner, delivering the result to a Partner without a current Authenticated_Session when that Partner next establishes an Authenticated_Session.
11. WHILE an Asynchronous_Game_Session has not reached a terminal state and its Pairing has not been dissolved, THE System SHALL keep the Asynchronous_Game_Session active regardless of the duration of Partner inactivity and SHALL continue the Asynchronous_Game_Session until it reaches a terminal state or the Pairing is dissolved.
12. WHEN a Turn has remained pending for the Active_Turn_Holder for 48 continuous hours in an active Asynchronous_Game_Session without the Active_Turn_Holder taking that Turn, THE System SHALL deliver a reminder Notification to the Active_Turn_Holder indicating that it is that Partner's Turn, within 5 seconds while that Partner's Client has network connectivity and otherwise when that Partner next establishes an Authenticated_Session, and SHALL keep the Asynchronous_Game_Session active without terminating or forfeiting the Asynchronous_Game_Session.

### Requirement 8: Quizzes

**User Story:** As a paired user, I want to take themed, scored quizzes with my partner where I answer for myself and then guess my partner's answers, so that we can learn about each other and see how well we know each other.

#### Acceptance Criteria

1. WHILE a User is in a Pairing, THE System SHALL present the list of available themed Quizzes to both Partners.
2. WHEN a User in a Pairing selects an available Quiz to start and no active Quiz_Session exists for that Pairing, THE System SHALL create a Quiz_Session associated with the Pairing in the self-answer phase with no recorded Self_Answers, no recorded Guesses, and a Score of zero for each Partner.
3. WHILE a Quiz_Session is in the self-answer phase, WHEN a Partner submits a valid Self_Answer for a Quiz_Question that the Partner has not yet answered, THE System SHALL record the Self_Answer for that Partner, where a valid Self_Answer is a selection of exactly one of the offered choices for a multiple-choice Quiz_Question or a non-empty text of 1 to 100 characters for a short-answer Quiz_Question.
4. WHILE a Quiz_Session is in the self-answer phase, THE System SHALL withhold each Partner's Self_Answers from the other Partner.
5. WHEN both Partners have recorded Self_Answers for all Quiz_Questions in a Quiz_Session, THE System SHALL transition the Quiz_Session to the guessing phase.
6. WHILE a Quiz_Session is in the guessing phase, WHEN a Partner submits a valid Guess for a Quiz_Question that the Partner has not yet guessed, THE System SHALL record the Guess as that Partner's prediction of the other Partner's Self_Answer, where a valid Guess is a selection of exactly one of the offered choices for a multiple-choice Quiz_Question or a non-empty text of 1 to 100 characters for a short-answer Quiz_Question.
7. WHEN a Partner records a Guess that matches the other Partner's recorded Self_Answer for the same Quiz_Question, THE System SHALL award one point to that Partner's Score for the Quiz_Session, where a match for a multiple-choice Quiz_Question is the identical choice and a match for a short-answer Quiz_Question is text that is equal after trimming leading and trailing whitespace and applying case-insensitive comparison.
8. WHEN both Partners have recorded Guesses for all Quiz_Questions in a Quiz_Session, THE System SHALL complete the Quiz_Session and present to both Partners each Quiz_Question together with both Partners' Self_Answers, both Partners' Guesses, and each Partner's final Score.
9. THE System SHALL ensure that each Quiz_Question belongs to exactly one Quiz and appears in no other Quiz.
10. IF a User attempts to start a Quiz_Session while not in a Pairing, THEN THE System SHALL reject the request and return an error stating that a Partner is required.
11. IF a User attempts to start a Quiz_Session while an active Quiz_Session already exists for the Pairing, THEN THE System SHALL reject the request, return an error indicating that a Quiz_Session is already in progress, and preserve the existing Quiz_Session.
12. IF a Partner submits a Self_Answer that is empty, that selects a choice not offered for the Quiz_Question, that exceeds 100 characters, or that is for a Quiz_Question the Partner has already answered, THEN THE System SHALL reject the submission, return an error identifying the invalid submission, and retain any previously recorded Self_Answer.
13. IF a Partner submits a Guess that is empty, that selects a choice not offered for the Quiz_Question, that exceeds 100 characters, that is for a Quiz_Question the Partner has already guessed, or that is submitted while the Quiz_Session is not in the guessing phase, THEN THE System SHALL reject the submission, return an error identifying the invalid submission, and retain any previously recorded Guess.

### Requirement 9: Relationship Date Management

**User Story:** As a paired user, I want to record important dates, so that my partner and I remember them.

#### Acceptance Criteria

1. WHEN a User in a Pairing creates a Relationship_Date with a non-empty title of 1 to 100 characters and a valid calendar date, THE System SHALL save the Relationship_Date to the Pairing and make it visible to both Partners within 5 seconds while both Partners' Clients have network connectivity.
2. WHEN a User in a Pairing edits an existing Relationship_Date with a non-empty title of 1 to 100 characters and a valid calendar date, THE System SHALL update the Relationship_Date and reflect the change for both Partners within 5 seconds while both Partners' Clients have network connectivity.
3. WHEN a User in a Pairing deletes an existing Relationship_Date, THE System SHALL remove the Relationship_Date and reflect the removal for both Partners within 5 seconds while both Partners' Clients have network connectivity.
4. IF a User attempts to create or edit a Relationship_Date with a title that is missing, empty, contains only whitespace, or exceeds 100 characters, THEN THE System SHALL reject the request, make no change to the stored Relationship_Dates, and return an error identifying the title as invalid.
5. IF a User attempts to create or edit a Relationship_Date with a missing calendar date or a calendar date that is not a valid calendar date, THEN THE System SHALL reject the request, make no change to the stored Relationship_Dates, and return an error identifying the calendar date as invalid.
6. IF a User attempts to edit or delete a Relationship_Date that does not exist in the Pairing, THEN THE System SHALL reject the request and return an error indicating that the Relationship_Date was not found.
7. WHEN a User in a Pairing views the Pairing's Relationship_Dates, THE System SHALL display them in ascending order by their next upcoming occurrence relative to the current date, and SHALL order any Relationship_Dates sharing the same next occurrence alphabetically by title using case-insensitive comparison.

### Requirement 10: Relationship Date Reminders

**User Story:** As a paired user, I want to be reminded of important dates, so that neither of us forgets them.

#### Acceptance Criteria

1. WHEN a User in a Pairing sets a Reminder on a Relationship_Date with a lead time between 1 minute and 365 days that resolves to a trigger time later than the current time, THE System SHALL schedule a Notification for both Partners to be triggered at the specified lead time before the Relationship_Date's occurrence.
2. IF a User attempts to set a Reminder with a lead time outside the range of 1 minute to 365 days, or with a lead time that resolves to a trigger time earlier than or equal to the current time, THEN THE System SHALL reject the request and return an error indicating that the lead time is invalid.
3. WHEN a scheduled Reminder's trigger time is reached, THE System SHALL deliver a Notification to each Partner's Authenticated_Session within 60 seconds of the trigger time, and otherwise deliver the Notification when that Partner next establishes an Authenticated_Session.
4. WHEN a Relationship_Date associated with one or more Reminders is deleted, THE System SHALL cancel all scheduled Reminders associated with that Relationship_Date so that no further Notifications for those Reminders are delivered.
5. WHERE a Relationship_Date is marked as recurring, WHEN a scheduled Reminder for the current occurrence is delivered, THE System SHALL schedule a Reminder at the same lead time before the next future occurrence of the Relationship_Date.

### Requirement 11: Notifications

**User Story:** As a user, I want to receive timely notifications, so that I stay aware of invitations, reminders, and partner activity.

#### Acceptance Criteria

1. WHEN a User receives a Pairing_Invitation, THE System SHALL deliver a Notification to the recipient's Authenticated_Session within 5 seconds while the recipient's Client has network connectivity.
2. WHEN a Partner sends a Game_Session invitation, THE System SHALL deliver a Notification to the invited Partner's Authenticated_Session within 5 seconds while the invited Partner's Client has network connectivity.
3. WHILE a User has disabled a Notification category in settings, THE System SHALL withhold Notifications of that category from that User's Authenticated_Session.
4. IF Notification delivery to a Client fails, THEN THE System SHALL retain the undelivered Notification for up to 30 days and deliver it when that User next establishes an Authenticated_Session within that period.
5. IF a retained Notification remains undelivered for 30 days after its creation, THEN THE System SHALL discard the Notification and make no further delivery attempts.
6. WHEN a User acknowledges a Notification on the User's Authenticated_Session, THE System SHALL mark that Notification as delivered for that User and withhold the same Notification from that User's subsequent Authenticated_Sessions.

### Requirement 12: Account Deletion

**User Story:** As a user, I want to permanently delete my account and my data from inside the app, so that I can leave the service entirely without contacting support.

**Rationale:** Apple App Store Review Guideline 5.1.1(v) requires any app that supports account creation to also offer account deletion initiated from within the app. Requirement 4 (Partner Unlinking) deliberately RETAINS each former Partner's individual data, so it does not satisfy this. Comparable obligations exist under GDPR Article 17 and similar regimes.

#### Acceptance Criteria

1. WHILE a User has an Authenticated_Session, THE System SHALL present a means to request Account_Deletion from within the Client, without requiring the User to contact support or leave the app.
2. WHEN a User requests Account_Deletion, THE System SHALL require the User to reconfirm the request before any data is removed, and SHALL state that the removal is permanent and irreversible.
3. WHEN a User confirms Account_Deletion for an Account that is in a Pairing, THE Pairing_Service SHALL dissolve the Pairing before removing the Account, applying every effect of Requirement 4 to the remaining Partner so that the remaining Partner is left in a consistent unpaired state and is notified that the Pairing has ended.
4. WHEN a User confirms Account_Deletion, THE System SHALL permanently remove that Account's credentials, its Account-owned data, and its Notifications, such that the Account's email address no longer identifies an Account and can be used to register a new Account.
5. WHEN a User confirms Account_Deletion, THE System SHALL terminate every Authenticated_Session for that Account and deny all subsequent requests presenting credentials or tokens for the deleted Account.
6. WHEN an Account is deleted, THE System SHALL remove the data owned by any Pairing that Account belonged to, including Game_Sessions, Quiz_Sessions, Self_Answers, Guesses, Relationship_Dates, Reminders, and stored images, so that no Pairing-owned content outlives the deletion.
7. WHEN a User confirms Account_Deletion, THE System SHALL complete the removal within 30 seconds and confirm completion to the User.
8. IF a User requests Account_Deletion and does not reconfirm, THEN THE System SHALL make no change to the Account or to any data.
