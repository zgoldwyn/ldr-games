# Requirements Document

## Introduction

The LDR Companion App is a cross-platform application (mobile and desktop) designed for people in long-distance relationships. Two people link their accounts into an exclusive one-to-one pairing and gain access to shared features: real-time two-player games, quizzes, and a shared calendar of important relationship dates with reminders. A user can be paired with exactly one partner at any given time. All games and quizzes are played online between the two paired partners.

This document defines the functional and quality requirements for the feature set. Implementation details (frameworks, protocols, data stores) are deliberately excluded and will be addressed in the design phase.

## Glossary

- **System**: The LDR Companion App as a whole, including mobile and desktop clients and supporting backend services.
- **Account**: A registered user identity with unique credentials.
- **User**: A person who owns an Account and interacts with the System through a client.
- **Client**: A mobile or desktop instance of the System used by a User.
- **Pairing**: An exclusive one-to-one link between two Accounts that grants access to shared features.
- **Partner**: The other User in a Pairing relative to a given User.
- **Pairing_Invitation**: A time-limited request generated by one Account to establish a Pairing with another Account.
- **Game**: A two-player interactive activity played in real time between the two Users in a Pairing.
- **Game_Session**: A single instance of a Game being played by both Partners.
- **Quiz**: A structured set of questions that Partners answer, used to compare or reveal answers.
- **Quiz_Session**: A single instance of a Quiz being taken within a Pairing.
- **Relationship_Date**: A calendar entry, owned by a Pairing, marking a date of significance (for example an anniversary or birthday).
- **Reminder**: A scheduled notification associated with a Relationship_Date.
- **Notification**: A message delivered to a User's Client to inform the User of an event.
- **Authentication_Service**: The System component responsible for verifying Account credentials.
- **Pairing_Service**: The System component responsible for creating, enforcing, and dissolving Pairings.
- **Sync_Service**: The System component responsible for keeping shared data consistent across a User's Clients and between Partners.

## Requirements

### Requirement 1: Account Registration

**User Story:** As a new user, I want to create an account, so that I can access the app and link with my partner.

#### Acceptance Criteria

1. WHEN a User submits registration details with a syntactically valid email address not associated with any existing Account and a password that is 12 to 128 characters long and contains at least one uppercase letter, at least one lowercase letter, at least one digit, and at least one non-alphanumeric character, THE Authentication_Service SHALL create a new Account, return a success confirmation within 5 seconds, and place the Account in an unpaired state.
2. IF a User submits registration details with an email address already associated with an existing Account, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error identifying the email as already registered.
3. IF a User submits a password shorter than 12 characters, longer than 128 characters, or missing at least one uppercase letter, one lowercase letter, one digit, or one non-alphanumeric character, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error describing each unmet password criterion.
4. IF a User submits registration details with an email address that is not in a valid email format, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error indicating that the email address format is invalid.
5. IF a User submits registration details in which the email address or the password is empty or absent, THEN THE Authentication_Service SHALL reject the registration, create no new Account, and return an error identifying each missing required field.
6. THE Authentication_Service SHALL store passwords using a one-way cryptographic hash and SHALL never store or return the plaintext password.

### Requirement 2: Account Authentication

**User Story:** As a registered user, I want to sign in securely, so that only I can access my account.

#### Acceptance Criteria

1. WHEN a User submits credentials consisting of an email address and a password that match an existing Account, THE Authentication_Service SHALL grant access, establish an authenticated session for that Client, and complete authentication within 3 seconds under normal network conditions.
2. IF a User submits credentials that do not match any existing Account, THEN THE Authentication_Service SHALL deny access and return an authentication-failed error that does not indicate whether the email address or the password was incorrect.
3. IF a User submits non-matching credentials for the same Account on 5 consecutive attempts within a 15-minute window, THEN THE Authentication_Service SHALL temporarily lock authentication for that Account for 15 minutes and return an error indicating that the Account is temporarily locked.
4. WHEN a User signs out, THE Authentication_Service SHALL terminate the authenticated session for that Client within 3 seconds.
5. WHILE a User has no valid authenticated session, THE System SHALL deny access to shared features and direct the User to the sign-in interface.
6. WHILE an authenticated session has had no User activity for 30 consecutive days, THE Authentication_Service SHALL invalidate the session and require the User to sign in again before granting further access.

### Requirement 3: Partner Pairing

**User Story:** As a user, I want to link my account with my partner, so that we can share games, quizzes, and dates.

#### Acceptance Criteria

1. WHEN an authenticated User who is not currently in a Pairing requests to invite a Partner, THE Pairing_Service SHALL generate a unique Pairing_Invitation that is valid for 72 hours from its creation.
2. WHEN a User accepts a Pairing_Invitation within 72 hours of its creation and neither Account is currently in a Pairing, THE Pairing_Service SHALL create a Pairing linking the two Accounts.
3. IF a User attempts to accept a Pairing_Invitation while already in a Pairing, THEN THE Pairing_Service SHALL reject the request, leave the pairing state of both Accounts unchanged, and return an error stating that the Account is already paired.
4. IF a User attempts to create or accept a Pairing_Invitation for an Account that is already in a Pairing, THEN THE Pairing_Service SHALL reject the request, leave the pairing state unchanged, and return an error stating that the target Account is already paired.
5. IF a User accepts a Pairing_Invitation more than 72 hours after its creation, THEN THE Pairing_Service SHALL reject the request, leave the pairing state unchanged, and return an expiration error.
6. THE Pairing_Service SHALL ensure that each Account is a member of at most one active Pairing at any time.
7. IF an authenticated User who is already in a Pairing requests to invite a Partner, THEN THE Pairing_Service SHALL reject the request and return an error stating that the Account is already paired.
8. WHEN a Pairing is created from a Pairing_Invitation, THE Pairing_Service SHALL invalidate that Pairing_Invitation so that it cannot be used to create another Pairing.

### Requirement 4: Partner Unlinking

**User Story:** As a user, I want to unlink from my partner, so that I can end the pairing or link with someone else.

#### Acceptance Criteria

1. WHEN an authenticated User in a Pairing confirms a request to unlink, THE Pairing_Service SHALL dissolve the Pairing and revoke shared-feature access for both Accounts within 5 seconds.
2. WHEN a Pairing is dissolved, THE Pairing_Service SHALL deliver a Notification to both former Partners' authenticated Clients indicating that the Pairing has ended.
3. WHEN a Pairing is dissolved, THE Pairing_Service SHALL set both former Partner Accounts to an unpaired state such that each Account may create or accept a new Pairing_Invitation.
4. WHEN a Pairing is dissolved, THE System SHALL retain each former Partner Account's individual data and revoke both former Partners' access to all data owned by the former Pairing.
5. IF a former Partner has no authenticated Client at the time a Pairing is dissolved, THEN THE Pairing_Service SHALL deliver the Pairing-ended Notification when that Partner next establishes an authenticated session.
6. IF a Game_Session or Quiz_Session is active for a Pairing when that Pairing is dissolved, THEN THE System SHALL terminate the active Session and notify both former Partners that the Session has ended.

### Requirement 5: Cross-Platform Access and Synchronization

**User Story:** As a user, I want to use the app on both mobile and desktop, so that my data stays consistent everywhere.

#### Acceptance Criteria

1. WHILE a User is signed in on both a mobile Client and a desktop Client, THE System SHALL present the same Account data on all of the User's authenticated Clients.
2. WHEN shared data is changed on one Client, THE Sync_Service SHALL propagate the change to the User's other authenticated Clients within 5 seconds while all of those Clients have network connectivity.
3. WHEN shared data is changed by one Partner, THE Sync_Service SHALL propagate the change to the other Partner's authenticated Clients within 5 seconds while both Partners' Clients have network connectivity.
4. IF a Client loses network connectivity, THEN THE System SHALL display a connectivity-lost indicator and retain all local changes in a synchronization queue until network connectivity is restored.
5. WHEN a Client regains network connectivity, THE Sync_Service SHALL synchronize all queued changes within 10 seconds of connectivity restoration and resolve conflicting changes to the same shared data item using a last-write-wins policy based on change timestamps.
6. IF two conflicting changes to the same shared data item have identical change timestamps, THEN THE Sync_Service SHALL apply a deterministic resolution so that all of the User's and both Partners' authenticated Clients converge to the same value.

### Requirement 6: Real-Time Two-Player Game Sessions

**User Story:** As a paired user, I want to play games with my partner in real time, so that we can have fun together across the distance.

#### Acceptance Criteria

1. WHILE a User is in a Pairing, THE System SHALL present the list of available Games to both Partners.
2. WHEN a User in a Pairing selects a Game and invites the Partner, THE System SHALL create a Game_Session in a pending state and deliver an invitation Notification to the Partner within 5 seconds while both Clients have network connectivity.
3. WHEN both Partners have joined a pending Game_Session within 60 seconds of the invitation, THE System SHALL transition the Game_Session to an active state, start the Game, and present identical game state to both Partners.
4. WHEN one Partner performs a valid move in an active Game_Session, THE System SHALL update the game state and reflect the move on both Partners' Clients within 2 seconds while both Clients have network connectivity.
5. IF a User attempts to start a Game_Session while not in a Pairing, THEN THE System SHALL reject the request and return an error stating that a Partner is required.
6. IF a Partner's Client has no network connectivity with the System for 30 continuous seconds during an active Game_Session, THEN THE System SHALL pause the Game_Session, deliver a Notification to the remaining Partner, and preserve the current game state.
7. WHEN a disconnected Partner rejoins a paused Game_Session within 5 minutes of the pause, THE System SHALL resume the Game_Session from the preserved game state and present identical game state to both Partners.
8. WHEN a Game_Session reaches a terminal state, THE System SHALL record the outcome and present the result to both Partners.
9. IF the invited Partner does not join a pending Game_Session within 60 seconds of the invitation, THEN THE System SHALL cancel the Game_Session and deliver a Notification to the inviting Partner indicating that the invitation expired.
10. IF a disconnected Partner does not rejoin a paused Game_Session within 5 minutes of the pause, THEN THE System SHALL terminate the Game_Session, record it as ended without a completed outcome, and deliver a Notification to both Partners.
11. IF a Partner attempts an invalid move in an active Game_Session, THEN THE System SHALL reject the move, retain the current game state unchanged, and return an error indicating that the move is invalid.

### Requirement 7: Quizzes

**User Story:** As a paired user, I want to take quizzes with my partner, so that we can learn about each other.

#### Acceptance Criteria

1. WHILE a User is in a Pairing, THE System SHALL present the list of available Quizzes to both Partners.
2. WHEN a User in a Pairing selects an available Quiz to start and no active Quiz_Session exists for that Pairing, THE System SHALL create a Quiz_Session associated with the Pairing with no recorded answers for either Partner.
3. WHEN a Partner submits a non-empty answer for a Quiz question that the Partner has not yet answered in the active Quiz_Session, THE System SHALL record the answer for that Partner in the Quiz_Session.
4. WHILE only one Partner has submitted an answer for a Quiz question, THE System SHALL withhold that Partner's answer from the other Partner.
5. WHEN both Partners have submitted answers for a Quiz question, THE System SHALL reveal both Partners' answers for that question to both Partners' authenticated Clients within 5 seconds while both Partners' Clients have network connectivity.
6. WHEN both Partners have completed all questions in a Quiz_Session, THE System SHALL present a completed result listing each question together with both Partners' recorded answers to both Partners.
7. IF a User attempts to start a Quiz_Session while not in a Pairing, THEN THE System SHALL reject the request and return an error stating that a Partner is required.
8. IF a User attempts to start a Quiz_Session while an active Quiz_Session already exists for the Pairing, THEN THE System SHALL reject the request and return an error indicating that a Quiz_Session is already in progress, and preserve the existing Quiz_Session.
9. IF a Partner submits an empty answer or an answer for a Quiz question the Partner has already answered in the active Quiz_Session, THEN THE System SHALL reject the submission, return an error identifying the invalid submission, and retain the previously recorded answer.

### Requirement 8: Relationship Date Management

**User Story:** As a paired user, I want to record important dates, so that my partner and I remember them.

#### Acceptance Criteria

1. WHEN a User in a Pairing creates a Relationship_Date with a non-empty title of 1 to 100 characters and a valid calendar date, THE System SHALL save the Relationship_Date to the Pairing and make it visible to both Partners within 5 seconds while both Partners' Clients have network connectivity.
2. WHEN a User in a Pairing edits an existing Relationship_Date with a non-empty title of 1 to 100 characters and a valid calendar date, THE System SHALL update the Relationship_Date and reflect the change for both Partners within 5 seconds while both Partners' Clients have network connectivity.
3. WHEN a User in a Pairing deletes an existing Relationship_Date, THE System SHALL remove the Relationship_Date and reflect the removal for both Partners within 5 seconds while both Partners' Clients have network connectivity.
4. IF a User attempts to create or edit a Relationship_Date with a title that is missing, empty, contains only whitespace, or exceeds 100 characters, THEN THE System SHALL reject the request, make no change to the stored Relationship_Dates, and return an error identifying the title as invalid.
5. IF a User attempts to create or edit a Relationship_Date with a missing calendar date or a calendar date that is not a valid calendar date, THEN THE System SHALL reject the request, make no change to the stored Relationship_Dates, and return an error identifying the calendar date as invalid.
6. IF a User attempts to edit or delete a Relationship_Date that does not exist in the Pairing, THEN THE System SHALL reject the request and return an error indicating that the Relationship_Date was not found.
7. WHEN a User in a Pairing views the Pairing's Relationship_Dates, THE System SHALL display them in ascending order by their next upcoming occurrence relative to the current date, and SHALL order any Relationship_Dates sharing the same next occurrence alphabetically by title using case-insensitive comparison.

### Requirement 9: Relationship Date Reminders

**User Story:** As a paired user, I want to be reminded of important dates, so that neither of us forgets them.

#### Acceptance Criteria

1. WHEN a User in a Pairing sets a Reminder on a Relationship_Date with a lead time between 1 minute and 365 days that resolves to a trigger time later than the current time, THE System SHALL schedule a Notification for both Partners to be triggered at the specified lead time before the Relationship_Date's occurrence.
2. IF a User attempts to set a Reminder with a lead time outside the range of 1 minute to 365 days, or with a lead time that resolves to a trigger time earlier than or equal to the current time, THEN THE System SHALL reject the request and return an error indicating that the lead time is invalid.
3. WHEN a scheduled Reminder's trigger time is reached, THE System SHALL deliver a Notification to each Partner's authenticated Clients within 60 seconds of the trigger time.
4. WHEN a Relationship_Date associated with one or more Reminders is deleted, THE System SHALL cancel all scheduled Reminders associated with that Relationship_Date so that no further Notifications for those Reminders are delivered.
5. WHERE a Relationship_Date is marked as recurring, WHEN a scheduled Reminder for the current occurrence is delivered, THE System SHALL schedule a Reminder at the same lead time before the next future occurrence of the Relationship_Date.

### Requirement 10: Notifications

**User Story:** As a user, I want to receive timely notifications, so that I stay aware of invitations, reminders, and partner activity.

#### Acceptance Criteria

1. WHEN a User receives a Pairing_Invitation, THE System SHALL deliver a Notification to each of the recipient's authenticated Clients within 5 seconds while those Clients have network connectivity.
2. WHEN a Partner sends a Game_Session invitation, THE System SHALL deliver a Notification to each of the invited Partner's authenticated Clients within 5 seconds while those Clients have network connectivity.
3. WHILE a User has disabled a Notification category in settings, THE System SHALL withhold Notifications of that category from all of that User's Clients.
4. IF Notification delivery to a Client fails, THEN THE System SHALL retain the undelivered Notification for up to 30 days and deliver it when that Client next establishes an authenticated session within that period.
5. IF a retained Notification remains undelivered for 30 days after its creation, THEN THE System SHALL discard the Notification and make no further delivery attempts.
6. WHEN a User has multiple authenticated Clients and one Client acknowledges a Notification, THE System SHALL mark that Notification as delivered for that User and withhold redelivery of the same Notification to that User's other Clients.
